# KV 快照批量复制：Windows A770，2026-10-31

参考 [a770-qwen-xe1 issue #1](https://github.com/ef777/a770-qwen-xe1/issues/1) 的低成本验证顺序：先测主机快照的复制与缓存命中成本，再考虑改变 KV 驻留策略。该 issue 是建议，截至本次检查没有评论或 Intel 移植结果；其中的 dense 27B、PCIe 4.0 数字不作为本机 Flash-Next MoE、PCIe 3.0 的性能依据。Strata 已有 host KV、分页、动态 QSA 检索与循环状态检查点，本次只减少现有复制路径的等待。

不据此把动态检索改成每请求一次的固定窗口。所引用的 [ninfer-fusion-kvmem README](https://github.com/1314521gjy/ninfer-fusion-kvmem#readme) 记录了超池且关闭检索时 HTTP 200、答案貌似合理但命中 0/6 的反例；扩大逻辑上下文和接口成功均不能证明长上下文质量。循环状态检查点用于回退和分支恢复，也不等于 KV 检索必须受检查点间距限制。

候选将每个分段的同步改为每层一次同步。K/V、量化尺度和 indexer 数据仍走原有 in-order 队列；保存或恢复成功返回前，复制已经完成。没有改动数值内核、KV 格式、检索策略或模型权重。

保存先检查全部源缓冲区与复用范围，再分配全部目标缓冲区，最后提交复制。这样，后续分配失败不会释放先前复制仍在使用的目标；末尾源缓冲区缺失也不会覆盖已有快照的缓冲区内容。提交失败先排空队列；等待失败保持致命错误，不能在无法证明 GPU 已完成时释放主机缓冲区。

Windows Orca 原生 Level Zero 隔离构建的原版检查通过 4280 项，候选通过 4392 项。新增检查验证源缓冲区缺失时已有快照的缓冲区内容不被覆盖；原有检查覆盖 FP16、INT8、Q4、K8V4、分页与 ring 状态、GDN/indexer 状态和文件往返。新复制测量还会在下一次 GPU 同步之前检查保存结果，并检查常驻布局的恢复返回时队列已经完成。

本机单层复制已完成两次相邻 A/B/A 配对。FP16 的 8K 保存耗时降低 23.5%～25.7%，恢复降低 21.4%～22.0%；64K 保存和恢复也通过两次配对及漂移检查。以下时间均为单层快照，不是完整模型 TTFT。完整模型的 RAM 缓存命中 TTFT 也已通过两次配对，见下文；当前默认程序与配置未因本候选改变。

| FP16 / 8192 | 保存 | 4.561 / 4.552 ms | 3.387 / 3.482 ms | 25.749% / 23.507% |
| FP16 / 8192 | 恢复 | 4.770 / 4.774 ms | 3.721 / 3.753 ms | 21.980% / 21.380% |
| FP16 / 32768 | 保存 | 14.712 / 14.825 ms | 10.610 / 10.089 ms | 27.883% / 31.948% |
| FP16 / 65536 | 保存 | 28.415 / 28.299 ms | 19.070 / 19.042 ms | 32.887% / 32.714% |
| FP16 / 65536 | 恢复 | 30.288 / 30.206 ms | 20.810 / 21.056 ms | 31.292% / 30.292% |

24 个格式/容量/方向组合中，以上 9 个通过。其余 15 个至少一轮的相邻基线漂移超过 3%，不作收益或回退验收；例如 FP16/32768 恢复的首轮漂移为 −5.918%。所有原始数值与失败配对保留，不通过跨格式平均值消除漂移。五个复制进程各通过 1242 项数据与完成状态检查，共保留 540 个测量样本。

复制测量使用同一批已冻结的库与 GPU 内核，按 A/B/A/B/A 运行四种 KV 格式、8192/32768/65536 cells 的单层快照，每种形状预热三次、保留九次。单层为 2 个 KV head、head_dim 256、4-cell 页，indexer 为 128 维、每 4 cells 一块；主机缓冲区按最多 16 MiB 分段。它只测复制组件，不证明 32K/64K 完整模型请求的速度或质量。相邻基线漂移上限 3%，候选需两轮分别达到 1% 才计作该形状的复制吞吐收益。

原始 `bytes` 来自 `ConversationKv::bytes()`，是含分段目录的主存分配量，不是 PCIe 搬运字节。五臂相同形状的该值一致；本报告只比较耗时，不据此计算硬件带宽。

真实会话对照另以当前已验收默认版本为基线，只替换快照对象。固定 FP16、专家缓存、MTP 和会话预算，检查 Code2K/Long8K 交替恢复的完整 128-token 输出、草稿工作量、复用长度、TTFT、decode、完整请求耗时、退出码和每秒物理显存样本。该组是缓存路径的匹配配置，不能代替生产默认配置的速度结论。

此处 `--spec 2 --mtp-max-t 1` 将 MTP 窗口限制为单 token；实测 accepted/offered 均为 0。该配置验证普通解码下的 RAM 会话缓存路径，不验证生产默认 MTP 投机解码的性能。

`model-v3` 完成 A/B/A/B/A 五臂，每臂先做 16-token 短请求预热，再交替运行 2048-token Code 与 8000-token Long 输入各四次，每次完整生成 128 token；首轮冷请求不参与热请求统计。40 个完整请求的输出均与各自的首个冷请求逐 token 一致，所有臂的复用量、草稿计数和结束原因一致；每臂都有 6 次实际 RAM 恢复，共 30 次。五个引擎均退出 0，1 Hz 物理显存样本的全程最低空闲为 2131.45 MiB。采样不证明亚秒级峰值。

热请求的 TTFT 中位数按相邻原版的几何均值配对。两次配对的基线漂移均不超过 3%，两种输入的 TTFT 耗时降低均达到预先设定的 1% 门槛：

| 输入 | 原版 TTFT，两次配对 | 候选 TTFT | 耗时降低，两次 | 基线漂移，两次 |
| --- | ---: | ---: | ---: | ---: |
| Code / 2048 tokens | 603.119 / 605.570 ms | 587.607 / 594.789 ms | 2.572% / 1.780% | −1.477% / +2.326% |
| Long / 8000 tokens | 640.840 / 638.164 ms | 620.103 / 623.907 ms | 3.236% / 2.234% | +1.210% / −2.019% |

没有任何 decode 或完整请求 wall 指标在两次配对中均达到 1% 的吞吐收益门槛；本次确认的是 RAM 缓存命中 TTFT 收益。该结果不证明冷请求、生产默认配置或 32K/64K 完整模型请求的性能收益，也不增加已经验证的上下文长度。

首个 `model-v1` 在生成请求之前停止：控制器沿用旧构建的 6297 槽假设，当前匹配配置实际分配 5802 槽，READY 空闲 1784 MiB；引擎正常退出 0。它没有生成或性能结果，不是候选速度失败。后继 `model-v2` 保持请求参数不变，记录 A0 的实际运行设置并要求其他进程完全一致，显存空闲值另行按 1024 MiB 门槛检查；原失败保留。

`model-v2` 在原版 A0 的首个 Code2K 请求后触发显存门槛：生成完整 128 token、退出码 0，但 70 个 1 Hz 样本中物理空闲最低仅 831.23 MiB，候选尚未运行。这组不作为性能验收。`model-v3` 将两臂请求的专家缓存同时降为 4500，首臂实际为 4717 槽 / 6480 MiB；保持输入、128-token 输出、上下文、KV 格式及 1024 MiB 门槛不变，继续要求全部实际运行设置与 A0 一致。两次配置的性能不混算。
