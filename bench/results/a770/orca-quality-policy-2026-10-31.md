# Orca 质量口径修正（2026-10-31）

完整分布的原始 PPL 作为质量门槛，条件 PPL 只用于诊断。旧 1022 个目标的 +6.94% / -7.41% 两项实测保留；按新门槛，旧结果不通过。它原先通过的是条件 PPL 门槛，不能据此宣称质量等价。

## 两种数字为何反向

非结束目标的 `原始 NLL = 条件 NLL + 结束概率惩罚`，其中惩罚为 `-log(1-p_end)`。条件分布是在假定不结束的条件下重新归一化，去掉了模型提前结束的代价。

| 旧输入前缀 | 目标数 | 原始 PPL 变化 | 条件 PPL 变化 | 结束概率惩罚变化（nat / 目标） |
| --- | ---: | ---: | ---: | ---: |
| Code2K | 511 | +3.3139% | -1.0290% | +0.042945 |
| Prose2K | 511 | +10.6912% | -13.3711% | +0.245111 |
| 合计 | 1022 | +6.9389% | -7.4055% | +0.144028 |

这些目标在 user 输入内部，尚未进入 assistant 回合。Prose 的结束概率惩罚增加，超过条件 NLL 的改善，因此完整分布评分退化。该差异不能靠改用条件 PPL 消除。[原始评分与历史门槛](../../../sycl/orca/deployed-versions-a770-windows-2026-10-31.json)保持原样；新旧判定分开记录。

## 当前验收方法

`tools/bench_orca_upgrade.py` 现在只以原始 PPL 判定：合计不升超过 1%，每场景不升超过 3%。合计先按目标数加权平均 NLL 差，再取指数，不平均场景百分比。原始、条件和结束概率惩罚三个 NLL 差及两个 PPL 变化同时输出；方向相反时显式标记。原始门槛失败会停止后续测速，并保留失败评分。

任一必需场景存在非有限值或缺分时，整组失败，不计算有效子集的合计 PPL。其他独立冷进程诊断仍采集，供定位使用；分别记录计划目标数、各端有效目标数和失败场景，不能把“检查执行完成”写成“质量通过”。

评分使用[固定 assistant 续写](orca-assistant-corpus.json)：short / code / gcd / memory / followup / prose / long 共 502 个目标，包含 2K / 8K 提示及完整聊天头。参考来自已冻结的模型输出，用于概率回归筛查，不是人工答案正确率基准。每个后端每个场景独立冷进程，完整输入相同，生成的一个诊断 token 不作评分目标。

诊断双方使用相同固定专家缓存容量，关闭自适应换入、PCIe 分摊和 prefill 借用；保留各自冻结的计算环境。通过现有 turn split 对长提示做批量 prefill、对固定续写采集 teacher-forced 分数。解析器逐项核对位置、目标 ID、全部应有日志与有限概率，漏行、重复、错位或额外行均拒绝。短提示的 user / assistant 头日志也核对，但只有 assistant 续写计入 PPL。原始 TSV、SHA256、逐目标分数、实际缓存容量及诊断参数写入 JSON。

两处真实日志边界也已覆盖：prompt 内 `<|im_end|>` 目标的条件概率本来未定义，只检查该位置的完整分布分数；旧 SYCL 在 Windows 长提示前会记录一个实际窗口的预热前缀，按明确日志标记和 INFO 窗口大小单独核验，不计入 assistant 目标。任意其他额外行仍拒绝。

这项检查与原部署配置的性能测量分开；改变评分边界和缓存后，不把新结果回填到旧 48 请求表。即使筛查通过，`quality_equivalence_established` 仍为 false。固定续写没有覆盖所有自然结束行为、任务准确率、采样和热历史，也未隔离各计算路径的贡献。

性能比较继续公开完整输出及 accepted / offered / reused / resume / finish。输出或工作量不同的整版本速度变化不能称作纯运行时提速；同源码后端归因仍使用[逐 token 和工作量一致的独立对照](orca-l0-2026-10-31.md#补充同源码后端对照)。

## A770 完整诊断：整组未通过

Windows A770 16 GB、驱动 32.0.101.9034；对照旧生产 SYCL 与本轮冻结的 FP16 pair Orca 默认构建。双方配置匹配 `spec-min-p=0.5`、3072 MiB 预留，诊断请求 3000 专家槽，实际均为 **3134 槽 / 4320 MiB**。这是较新构建与受控评分路径，和旧速度表的 0.8 门槛、自动缓存实验分开。

| 场景 | 计划目标 | SYCL 评分 | Orca 评分 | 原始 PPL 变化 | 条件 PPL 变化 |
| --- | ---: | --- | --- | ---: | ---: |
| short | 75 | 有限、完整 | 有限、完整 | -0.0270% | -0.0265% |
| code（2K） | 128 | 有限、完整 | 有限、完整 | -4.1293% | -4.1293% |
| gcd | 31 | 有限、完整 | 有限、完整 | +0.2288% | +0.2342% |
| memory | 6 | 有限、完整 | 有限、完整 | +0.0118% | +0.0105% |
| followup（8K） | 6 | 6 个目标非有限 | 有限、完整 | 不计算 | 不计算 |
| prose（2K） | 128 | 有限、完整 | 有限、完整 | -5.2574% | -5.2574% |
| long（8K） | 128 | 128 个目标非有限 | 有限、完整 | 不计算 | 不计算 |

两端各计划 502 个目标。Orca 全部有效；SYCL 有效 368 个，另外 134 个目标为 NaN。**整组失败，不输出有效子集的合计 PPL。** 表内五个可比较场景仅作诊断，两口径方向一致，最大差距约 0.0054 个百分点；它们不豁免两项 8K 失败，也不能为旧速度样本提供质量等价证明。

两项失败在批量 prefill 后首个可见评分位置 7993 已出现 NaN，生成的诊断 token 为 0；进程正常退出。该位置仍在 assistant 头中，实际固定续写目标从 7999 开始。日志只能限定首次可见异常，尚未定位出错算子或根因。另一次相同输入、参数与 EXE 的 3000 槽 followup 探针曾得到六个有限分数，后续未稳定重复，未计为修复或质量通过。

原始 TSV、逐目标分数、输入、两个冻结配置、EXE / 内核 / 脚本哈希、失败位置和独立探针见[完整质量 JSON](../../../sycl/orca/assistant-quality-policy-a770-windows-2026-10-31.json)。沿用同条件下已关闭的四项有效基线日志及失败 followup 日志，其余两项基线和七项候选以独立冷进程补齐；复用日志逐文件核对 SHA256。关闭日志再解析、目标覆盖与概率重算、配置 / EXE / 内核完整性审计均通过。`quality_evaluation_complete=true`、`quality_comparison.passed=false`，质量等价仍未建立。全程未将诊断计时作为速度证据，也未采集覆盖全部这些进程的物理显存最小值；INFO 容量不是运行时最低余量。

## 可运行检查

```powershell
python -X utf8 tools/test_bench_orca_upgrade.py
python -X utf8 tools/bench_orca_upgrade.py --baseline-config baseline-frozen.json --candidate-config candidate-frozen.json --out build-orca-quality-new --quality-only --quality-cache-slots 3000
```

两个配置的模型参数和 tokenizer 必须完全相同；保留各自 exe、库目录及环境。`--quality-cache-slots` 仅设置双方诊断缓存的请求槽数，实际分配可能不同于请求值，工具检查两端报告的容量一致；默认请求 3000 槽，为本次 A770 的 8K prefill 留空间。输出目录必须不存在，GPU 使用工作区共享锁。省略 `--quality-only` 才会在质量通过后执行部署配置的 A/B/A 性能测量。

较小缓存不构成 NaN 根因修复：同机旧 SYCL 在 3000 槽的一次独立 followup 探针中得到有限评分，但随后的整组复测再次出现非有限值，不能采用这次单独成功来豁免失败。默认槽数仅用于显存余量，所有有限值和覆盖门槛仍执行。

CPU 检查覆盖旧 1022 目标的拒绝、原始退化而条件改善、单场景失败、目标数不等时的加权、评分覆盖错误、保留非有限场景并拒绝子集合计，以及质量失败后不启动测速。此 CPU 检查通过只表示这些约束已被正确执行。
