# 行内代码正确性修复的 CPU 开销（2026-10-24）

比较上一轮行内代码修复前后冻结的 `OutputParser` 完整解析过程，输出必须相同。Windows、Xeon E5-2696 v4、Python 3.11.9；文本预先按 8 字符分块，计时包括解析器创建、增量解析、事件收集及 finish，排除分块生成和正确性断言。每臂预热，同进程 A/B/A、每臂 7 个样本；B 的中位数对比两个 A 中位数的几何平均，基线漂移绝对值超过 3% 的比较弃用。两轮独立运行，不使用 GPU 或模型。

下表为耗时变化，正值表示变慢；未把小幅负值认定为稳定优化。

| 场景 | 字符数 | 第一轮 | 第二轮 |
| --- | ---: | ---: | ---: |
| 普通回答文本 | 28,499 | 弃用：基线漂移 −5.09% | 弃用：基线漂移 −3.30% |
| 普通推理文本 | 28,499 | −2.98%（8.464→8.211 ms） | −1.32%（7.959→7.854 ms） |
| 反引号密集的回答文本 | 25,999 | +29.70%（6.667→8.647 ms） | +24.79%（6.775→8.454 ms） |
| 反引号密集的推理文本 | 25,999 | +29.37%（7.564→9.785 ms） | +23.98%（7.352→9.115 ms） |
| 短字符串工具调用 | 94 | 弃用：基线漂移 −5.99% | −0.01%（约 0.0786 ms） |
| 长字符串工具调用 | 28,582 | −2.44%（17.028→16.612 ms） | −2.11%（16.443→16.096 ms） |

最近修复的主要收益是正确识别示例和真实调用。反引号密集文本的 CPU 解析耗时上升约 24–30%，绝对增加约 1.7–2.2 ms / 2.6 万字符；未测得新的模型 prefill、decode 或 HTTP 端到端收益。这些毫秒值不能换算成模型 tok/s，也不能与先前窗口读取实验的比例叠加。普通回答文本的两次比较均未通过漂移门槛，不据此判断快慢。
