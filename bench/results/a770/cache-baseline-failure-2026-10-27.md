# A770 缓存容量归因：控制组再次全零（2026-10-27）

A770 16 GB / PCIe 3.0 / Windows / DPC++ 2025.3.2 / driver 32.0.101.9034。

为解释此前约 31 tok/s 与当前约 28/26 tok/s 的差距，准备了当前同一 HC 上下文 EXE、同一修正 GDN 输出参考、融合全部关闭的 cache5500/6000 对照。小缓存实际 5771 槽，大缓存要求 6297 槽，READY 空闲至少 1500 MiB；原始 Code/Prose 各 2048 输入、完整 128 输出、草稿阈值 0.5、prompt-cache 0。先做两种容量的完整输出检查，再按 A1/B1/A2 和 1%/3% 门槛筛选。

**小缓存控制组已失败，大缓存未启动，也没有正式性能样本。因此本组不能证明容量收益、容量回退或解释全部历史速度差。**

| Short 初始化 | 16 | 是 | 否 |

实际 5771 槽，READY 空闲 2607 MiB。融合各分派标记均关闭；有限值/AB/HC 探针、decode 日志、剖析器关闭。检测到 Prose 全零后，runner 按输出门槛停止，退出码 1；自有引擎清理后的退出码也为 1，不能将其另解释为引擎自行崩溃。未启动大缓存、正式对照或监控，没有终止其他实验。保留完整参数、参考、Short/Code/Prose 协议和失败输出，不将正确 Code 的吞吐拼入有效配对。

此前同 EXE 融合筛选的 28/28 完整输出通过仍是该组的有效记录，但本次失败证明不能据此宣布间歇问题已经修复。两组证据都保留，见[融合筛选与基线沿革](gu-q8-hc-context-model-2026-10-27.md)。

初次排队后的预检还曾因跨轮完整进程环境摘要不同而在创建 protocol、启动引擎前停止，0 次性能样本。冻结配置和参考文件 SHA256 与前组一致，也没有未登记的编译器/设备覆盖项；未捕获具体发生差异的进程环境变量。保存原脚本为 `run-attempt1.py` 和记录 `preflight-attempt1.json`，随后仅将该门槛限定为实际计算配置、输入、参考、EXE 和未登记覆盖项。正式同组各臂仍共用一个清理后的环境；不隐去预检失败，也不声称完整父进程环境相同。

下一项仅做路径诊断：当前同 EXE、小缓存及完整输入/参考不变，四个新进程按 BF16 GPU widening OFF/ON/OFF/ON，各 Short16 后四轮 Code/Prose，固定 32 次长请求，保留全部失败；关闭计时、异常探针和融合。冻结源码中，共享专家 T>1/N1 标量门控可由现有 `STRATA_PREFILL_BF16_GPU_WIDEN=1` 改走显式 widening/独立 C 分配，而 T1/N1 保留原计算。此为待验假设，不是已确认的分派日志、4 GiB 根因、修复或性能收益。
