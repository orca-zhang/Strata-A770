# A770：2K 连续解码基线与 40 tok/s 目标（2026-10-25）

当前生产版测得 **Code 24.85、Prose 24.55 tok/s**，尚未达到 40 tok/s。输入均为既有的 2048 个 token，完整生成 128 个 token，提示缓存关闭。每组保留三次，输出逐 token 相同。

| 场景 | decode 中位数 tok/s | 完整范围 tok/s | 达到 40 所需吞吐增幅 |

| Code2K | 24.854 | 24.743–24.856 | +60.938% |
| Prose2K | 24.546 | 24.420–24.819 | +62.959% |

A770 16GB、E5-2696 v4、PCIe 3.0 x16，Windows、驱动 32.0.101.9034、oneAPI 2025.3.2。生产 XMX v2 构建，FP16 KV、GDN/QSA Q8 tail、spec4、完整 248320 行草稿词表、上下文与 prefill chunk 均为 8192；专家缓存请求 5500、实际 5771 slots。保留原生产的自适应缓存、PCIe 比例 0.16 和 32 MiB prefill 工作区。

持有共享 GPU/编译锁，正常进程优先级，每请求前后检查竞争进程。先运行 Short/16 初始化，然后两场景各预热一次，再交错运行三轮保留请求。性能组关闭所有额外剖析。原始请求、输出、协议、环境和哈希保存在冻结目录；公开 JSON 包含全部八次 2K 请求，包括预热。这里只建立本轮基线，未作新旧引擎相邻对照；历史 Q8 KV 构建的约 29 tok/s 不作为本轮增益分母。

另起进程采集主机阶段计时，Code/Prose 分别记录 verify 89.25/81.89 ms 每窗口、草稿 11.89/11.92 ms 每窗口；verify 约占该诊断请求窗口总耗时的 85.45%/84.41%。verify 包含主机提交、权重访问和 GPU 等待，不是某个核函数的独占时间，也不是 CPU 计算占比。诊断进程只有 Short 初始化、没有相同的长输入预热，不能用其速度与性能组计算剖析开销。

原采集脚本误把较新版的 GPU 阶段采样能力当成旧生产 EXE 也支持。旧 EXE 明确报告 Windows EAGER 禁用阶段等待，因此原检查在要求 GPU 阶段日志时失败。保留该脚本和全部记录；完整的非剖析计时、计数、输出及证据哈希已另行审计，未重采样或改写冻结记录。

下一步比较已含 GDN 跨层提交、QSA 索引批量提交和原生 XMX 的较新冻结引擎，并使用它支持的 GPU 阶段采样定位 verify。构建之间还存在其他差异，结果须按完整构建比较，不能将收益单独归因给某个算子。[INT8 混合融合复测](int8-hybrid-stability-2026-10-25.md)仅 7/21 通过，未采用，也不用于宣称达到解码目标。
