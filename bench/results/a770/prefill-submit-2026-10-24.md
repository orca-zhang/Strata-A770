# A770 prefill 提交开销实验（2026-10-24）

共享 USM 内存池的同 EXE A/B/A 三轮 2K 请求全部超时，尚未确认整模型提速。生产程序和配置没有更改。

硬件：A770 16 GB、Xeon E5-2696 v4、Windows、PCIe 3.0 ×16；oneAPI 2025.3、oneMKL 2025.3。使用 10 月 21 日冻结的私有 EXE，IQ2_XS、FP16 KV、实际 4191 个专家槽；输入 2048 token，请求输出 16 token。

| 模式 | 完成请求 | 生成 token | 含退出清理的墙钟时间 |
| --- | ---: | ---: | ---: |
| 基线 | 0 | 0 | 159.84 秒 |
| 共享内存池 | 0 | 0 | 158.61 秒 |
| 基线 | 0 | 0 | 159.77 秒 |

每轮运行上限为 150 秒，墙钟时间还包括超时轮询和进程退出。三轮均完成了 6 token 的窗口初始化，但没有完成后续的 2K 请求。不能用上述超时时间计算吞吐提升或劣化。

候选仅设置 `UR_L0_USM_ALLOCATOR=1;64M;shared:1M,8,64K`。测试持有工作区 GPU 锁，周期性进程检查未发现其他 GPU/编译任务。这个结果只说明该设置未能让请求在期限内完成，不能排除其他分配开销。

另有独立 oneMKL `gemm_batch` 实验：FP16 输入、FP32 输出，覆盖 gate/up 和 down、统一 40 行及不同专家行数。最初版本只完成编译和链接；随后第一次 GPU 校验因输出行内填充区被写零而失败，未进入计时。单次和批量 GEMM 的有效输出及 CPU 参考样本一致，二者均写零相同填充区。后续改用生产代码实际的连续行布局，保留矩阵尾部保护检查，通过了校验；批量调用未确认稳定收益。后续大块 Host/Device/Shared RW 内存池确认了独立 GEMM 收益，但原 2K 请求仍超时，详见[后续数据](batch-gemm-2026-10-24.md)。原始记录保留。
