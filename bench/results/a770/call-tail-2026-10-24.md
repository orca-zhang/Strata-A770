# 工具调用结束标签增量检查（2026-10-24）

## 改动与范围

`serve/frontend.py` 的 `OutputParser.feed` 以前每收到一个片段就调用 `call_end`。即使没有完整结束标签，也会搜索整个累计缓冲区；参数里一旦出现字面的 `</tool_call>`，还会反复遍历参数。

现在先检查新片段是否包含 `>`，再在片段及前面的 `len(CALL_END) - 1` 个字符中检查结束标签。只有新标签完整到达才调用原有的 `call_end`；标签是否属于参数内容仍由原有规则判断。检查位于普通调用和 reasoning 调用分支，未增加解析状态或依赖。

这是 CPU 完整解析链的优化。累计字符串复制、raw 参数的扫描和 reasoning 的 `</think>` 搜索仍然存在，整个解析器的最坏复杂度未改变。本轮没有模型 prefill、decode 或 HTTP 端到端的新测量，不加入 README 性能表。

## 测量方法

- Intel Xeon E5-2696 v4、Windows、Python 3.11.9；共享机器负载未受控。
- 同一进程 A/B/A，仅切换 `OutputParser.feed` 方法；A 从本轮开始时的源码快照通过 AST 加载，其余代码相同。
- 每次完整解析都包含 `finish()`、事件收集及正确性断言。输入按 8 字符分块；字符串调用验证最终参数与拼接后的流式 JSON 一致，reasoning 调用验证没有发出流式参数，普通内容验证完整文本。
- 每组 7 个样本，取中位数；基线为前后 A 中位数的几何平均。两种方法各预热一批；短调用每样本解析 2,000 次，普通长参数和普通内容 10 次，其余 1 次。
- 前后 A 的相对漂移绝对值超过 3% 时排除该组，不据此报告收益。减少百分比表示耗时下降，不是吞吐量增幅。

## 回归检查与测试修复

- 新增 `ToolCallTerminators.test_call_closing_at_every_split`：在每个字符处分两次输入，插入空片段，覆盖两个连续调用、参数内字面结束标签、Unicode 空白、普通输出/reasoning、流式/非流式工具参数及调用 ID 对应的 JSON。
- 最终实现与冻结基线做了 5,000 组随机流式对照（种子 20261024）。逐个比较每次 feed 的事件、参数、异常、缓冲区、状态及 rescued/refused 计数；覆盖任意分块、空片段、截断、代码围栏、不同结束原因和未声明工具，结果一致。随机生成的 UUID 不参与跨次比较。
- 首次全量服务端发现并运行 466 项，耗时 533.925 秒：455 通过、3 失败、8 跳过，没有错误；运行期间服务端源文件哈希保持一致。3 项失败均为测试时序问题，完整记录保存在 `build-sycl-a770-call-tail-20261024/regression.log/json`，不把这轮记为全绿。

修复了三个失败，并检查了同类的短文件保存测试：

1. `RestartWindow.test_not_alive_until_ready` 原来把 `proc` 从旧进程变为 `None` 当作已启动新进程；等待 0.2 秒后读到了初始化期间的默认 context 4096。现在等待真实的新进程及 context 0，再检查 READY 前不可用；清理时等待重启线程，并关闭该类另一个 HTTP 测试的监听 socket。
2. 两个会话成功测试分别依赖 0.2 秒小于 0.3 秒、0.7 秒小于 1 秒，负载下实际唤醒太晚导致 500。成功 HTTP 用例现在直接送出合法的 SESSION/SWAIT/最终结果；新增模拟时钟用例验证跨越普通期限后的心跳续期、连续 SWAIT 的独立额度和 SESSION 后恢复普通期限。超时失败、HTTP 错误与引擎结束检查仍由相应用例执行。

时序修复后运行 **181 项定向回归**，耗时 **50.550 秒**：180 通过、1 项 Windows 符号链接权限条件跳过，无失败或错误，运行期间服务端源文件哈希保持一致。包含 frontend、reasoning tools/rescue、Responses API、相关服务端 HTTP 类、RestartWindow 以及完整 slots 模块。当前全量发现数为 467，未在测试修复后重新运行全部 467 项。

新增模拟时钟检查还做了两次错误注入：去掉 SESSION 的期限重置、忽略 SWAIT 等待额度，均被检查捕获。生产超时实现未修改；最后的 `frontend.py` 与最终计时快照相同。计时后变动仅涉及测试文件，计时用的冻结测试快照保留。
