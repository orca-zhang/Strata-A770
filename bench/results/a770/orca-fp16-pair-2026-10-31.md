# Orca L0 的 FP16 双专家预填充

2026-10-31，Windows、A770 16 GiB、Xeon E5-2696 v4、oneAPI 2025.3.2、Level Zero SDK 1.33.1。

原生实现、完整构建、数值检查、完整模型验收和实际服务器引擎验证已通过。A770 上两轮独立对照的预填充吞吐提高约 15.7%–16.4%，整请求耗时减少约 11.8%–12.6%；生成速度没有确认收益。主配置被并行任务更新后予以保留，独立 Orca 配置已可用。

[原始结果与产物散列](../../../sycl/orca/fp16-pair-a770-windows-2026-10-31.json)包含构建来源、完整模型输入/输出、逐项评分、全部计时、原生模块审计、显存样本归属、失败记录、脚本和检查日志。

此前的 [SYCL 结果](openvino-fp16-pair-2026-10-31.md)对应独立冻结产物。本报告检查 Orca 自己的矩阵内核和调度；所有性能对照保留原生 M4 和 batch8。

## 实现

[原生实现](../../../sycl/orca/gemm.cpp)将不同权重的两个专家放入同一 GU 网格和同一 Down 网格，按两个实际行数分别分派。保留 Orca 的 4×8、SG8、NSG8、256 GRF、FP16 输入与隐藏值、FP32 累加和原 K 顺序。两个 SwiGLU 调用保持原样。

[预填充分派](../../../sycl/src/prefill/prefill.cpp)复用现有两个反量化槽和 GEMM 工作区，支持 batch8 的异步提交与完成边界。奇数余项使用原专家链。IQ 权重文件、专家缓存和传输格式保持不变，没有引入 INT8 或新依赖。`ProductBatch` 的同权重合批规则未改动。

开关为 `STRATA_PREFILL_FP16_PAIR=0|1`，未设置时关闭。要求 A770、native XMX、expert chain；Orca 支持现有 batch8，SYCL 的原有约束保持不变。

## 检查和测量

独立目录 `build-orca-fp16-pair-20261031/`冻结完整源码，经根 CMake 入口重新构建 EXE 和全部镜像。6 项 CTest 全部通过，并额外检查普通顺序引擎模式。新增原生检查进行了 294 次完整 GU/FP16 H/Down 缓冲区比较，覆盖不同权重、1/1、3/5、4/4、4/5、7/9、8/16、127/129 行、边界哨兵、异步提交、普通与放宽依赖图回放，以及无效输入拒绝。

新矩阵内核的 256 GRF 模式精确匹配一个导出内核。现有资源查询显示新矩阵和补齐内核均为 `private_bytes=0`、`spill_bytes=0`；矩阵另有 1024 B 动态局部存储。显式缓冲区复用不等于驱动总显存开销为零，运行时仍需实际采样。

模型功能检查完成 22 个贪心解码请求，使用完整 Short16、Code/Prose2K 各 128 输出、Long8K/128、长短交错与重复请求，另以 2048 token 分块检查 Long8K。每条完整输出和草稿工作量均与关闭开关的同一 EXE 对照，实际加载模块审计也通过。

固定目标诊断完成已有五个用例、每侧 368 个目标；Code/Prose 各有实际 2041 token 批量预填充，再检查全部 517 条窗口评分。两侧逐项评分字典完全相同，每个用例及合计 PPL 变化均为 0%，Top1 一致率 100%。诊断单独关闭自适应/PCIe 分担，使用一个末轮检查点；要求冷请求、目标位置完全覆盖、分数有限。

性能阶段使用相同安全配置的 OFF/ON/OFF/ON/OFF 独立引擎，每个 2K 用例一轮预热、两条保留的完整 128 输出。每个场景和指标独立判断两轮至少 1% 且相邻基线漂移不超过 3%。所有完整输出必须匹配功能基准；草稿数按正式 A1 的相同请求序号比较。草稿工作量有变化时，只判断预填充时间，TTFT、整请求和生成指标均不确认收益。

功能和质量阶段保存在 `acceptance-3072-completed-phases/`。正式计时重新独立运行，复用阶段前检查配置、EXE、全部镜像、工具、评分语料及旧脚本的散列和成功退出状态，结果中的 `phase_lineage` 保留原始结果、脚本和日志散列。原始结果内的 `config` 是保留旧 EXE/镜像字段的配置模板；实际测试明确使用 `build-orca-fp16-pair-20261031/build/orca/strata.exe` 及同目录 `images/`，并由模块审计核实。

实际配置保留 batch8=1、packed4 value KV、MTP max=4、min-p=0.8、自动专家缓存、adapt-swaps=32、PCIe fraction=0.16。运行时以 1 Hz 采样物理显存，验收门槛为空闲至少 1024 MiB；亚秒峰值未测。35 tok/s 不作为本次完成条件。

## 显存校准及保留的失败

预留参数需要以运行时采样校准。初始 1536 MiB 在关闭优化的本轮程序中最低仅剩 490.773 MiB，代理停止了自己核实过的测试子进程；日志中的退出码来自这次主动停止。提高至 2560 MiB 后，22 个功能请求的完整输出与工作量均通过，开启侧后续历史最低仍降至 908 MiB。随后将两侧统一调整为 3072 MiB，重新验收；完成的功能和质量阶段最低采样空闲为 1337.012 MiB，最终门槛仍需合并正式计时样本。

这项校准会减少自动缓存的常驻专家数，且自动容量在各次引擎启动间存在变化。原 1536 MiB 关闭侧为 6518 个专家 / 8942 MiB；3072 MiB 功能关闭侧为 5497 / 7547 MiB，开启侧为 5181 / 7115 MiB。后面的收益只代表统一安全预留参数下的实测配置，不能算作相对原 1536 MiB 配置的升级收益，也不能声称两侧实际常驻容量完全相同。

另有两个验收工具问题保留了原始日志：采样次数最初超过工具的 3600 次上限，在执行请求前退出；评分脚本最初错误要求单 token 评分必须以 `length` 结束，已修正为允许正常的 `stop`。这些记录不计入提速验收，原生模型源码未因此更改。

3072 MiB 的首轮计时还暴露了跨历史比较草稿数过严的问题：Prose 的完整 128 个目标输出未变，接受/提议数却由 56/59 变为 55/58。该轮中止并保留日志，修正为上述按正式相同序号检查、按指标限制结论的规则后重新计时。保留正常的 lookup 和 MTP 配置，不为强行对齐草稿数而改变生产执行方式。
