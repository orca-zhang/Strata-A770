# A770：为什么 HC-up 单算子约 4 倍，请求收益仍很小

当前 U4×S4 接入仅替换主层 95 个 HC-up 投影，并融合 SiLU、BF16 舍入与 S4 打包。完整 HC 还包括 norm、down、inject、mix 和 write；MoE 专家链、注意力、权重搬运及 decode 均没有获得这项投影加速。算子最高约 3.9 倍使用驻留权重和重复命令图，初始化不计入热态时间；实际 prefill 为 T2047，不能直接套用 T1024 的倍率。

后续同步分阶段诊断把这个范围量化了：热态 Prose2K 的 HC-up 为 **281→104 ms，约 2.70 倍**，原阶段占比仅 **1.1%**。节省 177 ms，约为同步基线阶段总时间 25.45 s 的 0.70%。这与原先关闭诊断时单次 prefill 约 0.60% 的变化同量级，但不是独立确认该性能差异。

若被优化部分原占总耗时的 f、该部分加速 s 倍、新增开销为原总耗时的 h，则总加速比为 `1 / (1 - f + f/s + h)`。即使 s=4、h=0，f=2% 时整体吞吐只增加约 1.52%；要整体吞吐增加 20%，被优化部分原先至少要占 22.22%。这些是算术示例，不能当成 HC-up 的实测占比。

## 已有请求数据

机器为 A770 16 GiB、E5-2696 v4、256 GiB RAM、PCIe 3.0 x16，oneAPI 2025.3。以下来自此前未开启 profiling 的同一 EXE A1/B1/A2、固定 5771 槽诊断，每种场景每进程仅一次请求。基线列为 A1/A2 几何均值。

| 热态 Prose2K/128 | 原 BF16 基线 | U4 候选 |
| --- | ---: | ---: |
| prefill | 18.795 s | 18.683 s |
| decode | 5.046 s | 5.577 s |
| prefill + decode | 23.842 s | 24.260 s |
| 草稿接受数 | 72/96 | 68/99 |

prefill 的单次吞吐差约 +0.60%，prefill+decode 的单次吞吐差约 −1.73%。候选生成了完整 128 token，但输出不同；decode 差异不能用于判断未改动的 decode 内核回退，也不能仅凭接受数变化证明唯一原因。尚无固定目标 PPL 验收或独立性能确认。

首次 Code2K 包含 95 个文件加载、与原始 BF16 的 GPU repack 逐字节校验及分配，prefill 比基线多约 9.2%。热态算子倍率没有包含这项初始化。

## 存储与传输

当前高精度 HC 方案是两张 U4 权重平面，共 8.5 bit/weight，并用两张 S4 激活平面执行四个乘积。保留原 BF16 供 decode 使用后，packed payload 另外占约 315.43 MiB；没有因此节省显存。固定槽数的本轮诊断不能把这项开销描述为已减少专家槽位。

下一步专家链的单张 U4 格式为 4.5 bit/weight。三个官方 BF16 主层专家样本已完成直接转换和完整 CPU 解包检查，权重 NRMSE 约 10.8%～11.7%；这不等于模型质量。一个专家的 GU+down，U4 payload 为 2,764,800 字节，当前 IQ2_S/Q2_0 为 1,510,400 字节，搬运量约增加 83%。因此完整链必须同时计入 activation pack、SwiGLU 融合和 H2D，分别比较驻留和流式路径。

## 计时方法与边界

首次尝试复用原生事件分阶段计时，出现 GPU timeline 约 `3.689e13 ms`、墙钟约 `2.0e4 ms` 的不合理累计，整组排除出阶段归因。源代码使用无符号事件时间戳做差；仅凭日志尚不能确定驱动或事件行为的完整原因。

后续隔离诊断改用 `steady_clock`，在原有阶段标记处等待同一计算队列，并单独拆出 `hc up`。它保留完整输出检查与冷启动，但改变提交和搬运重叠；所得占比只能描述同步诊断，不能宣称正常运行的精确占比或请求提速。

热态 Prose2K 的同步诊断如下，阶段标签按现有实现记账：

| 阶段 | 原 BF16 ms | 占原阶段总时间 | U4 候选 ms |
| --- | ---: | ---: | ---: |
| HC-up + SiLU/pack | 281 | 1.1% | 104 |
| 其余 HC-read | 489 | 1.9% | 485 |
| 专家 GU→SwiGLU→down | 12420 | 48.8% | 12497 |
| 专家反量化 | 3231 | 12.7% | 3266 |
| 等待权重复制 | 1601 | 6.3% | 1632 |
| 全部已计阶段 | 25450 | 100% | 25379 |
| 对应 batched prefill 墙钟 | 25495 | — | 25426 |

`hc up` 包含全部 96 个主层位置，其中 `blk.44.hc_attn_up` 为原版回退；优化覆盖 95 个。专家链调用已融合，因此 `gemm gate/up` 标签包含整个 GU/SwiGLU/down，不能把它当作仅 GU 的耗时。时间包含提交、主机间隙和队列等待；各阶段的墙钟与 GPU kernel 时间不同。主机 staging 与计算可以重叠，不能另外加到时间线上。

冷态 Code2K 的 HC-up 段为 278→1505 ms，保留首次加载与绑定成本；这也是不能用热态算子倍率估计首次请求的直接证据。所有四个请求完整生成 128 token；两次基线全部匹配参考，两次候选非全零但输出不同。每场景每臂仅一次，不作质量或提速验收。

两组同步时间线分别为 26947/25450 ms 与 28097/25379 ms，都不超过对应墙钟，四组阶段总和仅有整数打印舍入差。首轮无效事件数据、修正后的源代码、完整 token 输出和未插桩诊断均保留在[数值记录](hc-u4-attribution-2026-10-27.json)中；[检查器](check_hc_u4_attribution_20261027.py)可独立复算。
