# Orca Direct：固定短代码性能差距诊断

2026-11-04，Windows 10 22H2、Intel Arc A770 16 GB、驱动 32.0.101.9034。
沿用[旧短代码锚点](orca-direct-anchor-2026-11-04.md)的 28-token 输入、76-token 自然输出、
5771 专家槽／7922 MiB、MTP4、`short-read=256`、`adapt-decay=0.95`。
主测结果仍是 **Direct 49.30、L0 56.24 tok/s，Direct 低 12.35%**；本报告的诊断不替换该测量或主图。

后续[缓存／复制引擎分离对照](orca-direct-copy-margin-2026-11-04.md)确认了主机策略差异：
专家替换热度差为 L0 1.5／Direct 0.5。仅对齐该常数，Direct 在自己的同期夹测中提升
10.29%，热态专家补入由 640 次／843.55 MiB 降至零；再用 BCS 的额外增益较小。
统一策略后的 BCS／L0 夹测仍相差 −3.04%，原测量及本报告的所有实验保持原样。

差距的一大部分已定位到**自适应专家补入与 MTP 草稿之间的调度干扰**。
MTP 的 GPU 执行跨度接近，但 Direct 每轮第二段草稿之前出现约 5 ms 的间隙。
关闭补入会消除大部分 MTP 差距，却让主模型因显存命中率下降而变慢。
把补入串行移到草稿之后也降低总吞吐，因此这两种改法均未采用。
这不足以证明 Direct 的架构上限，也没有证明当前 Direct 能替代 L0 的吞吐表现。

## `temperature=0` 与缓存

`temperature=0` 选择贪心采样，不开启回答缓存。CLI 锚点显式使用 `--prompt-cache 0`，
所有请求 `reused=resume=0`，每次重新计算 28-token 输入和完整输出。
两个后端均从独立进程开始，十次预热后才保留样本。

重复同一输入仍会固定输出和大部分专家路径，自适应缓存会把常用专家补入显存。
因此约 50 tok/s 是**固定输入的热态吞吐**，不能外推为冷请求或随机问题的速度。
命令图也会预热；图复用、专家驻留和回答复用是不同机制。

## 分阶段计时

同一已验证 Direct／L0 程序、原内核包，仅开启阶段计时，各十次预热、三次保留。
以下为最后三次的逐窗口中位数；每请求都是 20 个验证窗口、57／57 草稿接受。
计时开关和本轮没有并行显存监控会影响速率，诊断速率不与主图跨轮计算提升。

| 每窗口阶段 | L0（ms） | Direct（ms） | Direct 增量（ms） |
| --- | ---: | ---: | ---: |
| 验证 | 58.59 | 62.57 | 3.98 |
| commit／输出 | 0.10 | 0.23 | 0.13 |
| MTP 草稿 | 7.20 | 12.15 | 4.95 |

草稿部分约多 **99 ms／请求**，验证约多 **80 ms／请求**。
最后一个保留请求的验证 CPU 提交合计只有 L0 **0.699 ms**、Direct **1.574 ms**；
不能把约 190 ms 的整请求差距归结为提交函数的 CPU 执行时间。

验证阶段的显存命中也不同：最后三次 L0 为 **35165／36960（95.14%）**，
Direct 为 **34767、34756、34769／36960（约 94.04%～94.07%）**。
容量和输入相同不保证最终驻留集合相同。这可能贡献验证差距，但没有单独量化其因果份额；
剩余验证差距不能全部归因于缓存。

## MTP 的 GPU 时间戳

在两个已验证构建中，只重编译 MTP 的一个源文件，在每段草稿图前后加入有序 GPU 时间戳。
使用同一数值源、原头文件、其他对象和内核包，不混用不同版本的内联后端头文件。
Direct 采用该 A770 已校准的 **19.2 MHz／36 位**计数器；L0 按设备报告的 tick 周期换算。
时间戳包围的是 GPU 执行跨度，包含图内等待和调度，不是纯算术耗时。

| 每请求的 57 段草稿图，最后三次中位数 | L0（ms） | Direct（ms） |
| --- | ---: | ---: |
| 主机观测合计 | 143.09 | 242.18 |
| GPU 时间戳跨度合计 | 122.68 | 126.82 |

Direct 草稿的 GPU 跨度仅多约 **4 ms**；大部分约 **99 ms** 的差距在这些跨度之外。
另一个 Direct 提交／等待拆分诊断显示，第二段草稿提交中位数仅约 **0.095～0.106 ms**，
自身 GPU 跨度约 **2.10～2.12 ms**，主机却观测到约 **6.94～7.17 ms**。
前一段结束到这一段开始的 GPU 时间戳间隙为 **4.85～4.99 ms**；第三段的间隙只有 **0.27～0.30 ms**。
这些证据指向图之间的排队／调度间隙，不能称为第二段内核计算慢了 5 ms，
也不足以确定具体的 WDDM 内部调度策略。

## 已排查的改法

每个 clean OFF／ON／OFF 进程均十次预热、五次保留，使用同一候选 EXE；
对照为两侧中位数的几何平均。完整样本和漂移值见公开 JSON。

| 实验 | clean 对照（tok/s） | clean 候选（tok/s） | 结论 |
| --- | ---: | ---: | --- |
| Windows 1 ms 定时器精度 | 50.52 | 50.60 | 约 +0.16%，不能解释或追回原差距 |
| 监控栅栏最多忙等 5 ms | 50.79 | 50.73 | 约 −0.10%，没有收益 |
| 把专家补入移到 MTP 之后 | 49.83 | 47.96 | 本轮 −3.75%，未采用 |

定时器实验中，实际 C++ `sleep_for(25us)` 的中位数由约 **15.60 ms** 降到 **1.99 ms**，
但 decode 不变，因此不能把短休眠当作本次主因。
关闭独立投影调度也不能消除差距，诊断吞吐由 L0／Direct **57.60／50.42**
变为 **54.03／48.18 tok/s**。

关闭自适应路由收集／补入的四请求诊断仍保持全部输出及 57／57 草稿一致，
Direct MTP 降至 **7.69 ms／窗口**，但验证升至 **197.96 ms／窗口**，
decode 仅 **18.45 tok/s**。这验证了补入与草稿的干扰，也说明关闭专家补入不是可用修复。
该实验没有十次热身，不能与热态锚点比较整模型速率。

延后补入的候选保持原算法和容量，仍计算每轮应做的补入，只改变它与 MTP 的执行先后。
其单独计时臂最后三次 MTP 中位数为 **7.89 ms／窗口**，但整请求没有受益。
该 clean 对照的前后耗时漂移为 **+3.09%**，不应把 −3.75% 当成稳定退化幅度；
本轮没有支持采用这个改法的吞吐证据。后续若继续 Direct，优先验证显式复制引擎
能否在此锚点下减少计算队列竞争；已有其他配置的复制引擎实验不能直接当作本锚点的修复证据。

## 结论与可核对数据

目前没有追回原测量的 12.35% 差距，也没有发现 `temperature=0` 的回答缓存偏袒 L0。
需要当前已验证吞吐时，L0 是本锚点的性能首选；Direct 可以保留为独立实验路径，
不应据这次测试宣称比 L0 更快。是否继续投入应取决于复制队列优化能否带来完整请求收益，
不能只看 MTP 单个阶段变快。

[公开诊断数据](../../../sycl/orca/direct-gap-a770-windows-2026-11-04.json)保存 **258 次完整请求／19608 个输出 tokens**、
分阶段数值、逐图时间戳、构建命令、模块审计、原始日志哈希和可还原的实验脚本。
原始日志保留在本机 `build-orca-direct-gap-20261104/`。
所有试验使用共享 GPU 锁串行执行；主配置、已部署 EXE、内核包和原始专家 profile 未修改。
未采用任何诊断候选，没有新 PPL、通用工作负载或 Linux GPU 结论。
