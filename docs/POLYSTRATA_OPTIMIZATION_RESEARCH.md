# PolyStrata 优化调研：当前 A770 分支可以借鉴什么

调研日期：2026-11-03。对照 [PolyStrata 的 f472d85a](https://github.com/VecSzn/PolyStrata/tree/f472d85a30927301663401f7dc892e668578a90e) 与本地工作树，重点是 Windows、A770 16 GB、Qwen3.8-Flash-Next IQ2_XS、SYCL / Orca 路径。本地有未提交的实现，判断以实际文件为准。以下先记录源码调研，后续落地范围见文末：优先修改原生 DG2 与 Orca L0 共用的 Intel 主机代码。

**最值得进一步验证的是跨预填充块复用专家权重，以及减少缓存更新占用主线程的时间。** 专家热度及时落盘则是成本更小的启动优化。RAM 预算与按需锁页有参考价值，但对当前大内存、完整主存镜像的配置优先级低。

PolyStrata 分成沿用 Strata 的引擎和新增的 `strata-poly`。首页的高吞吐主要来自另一模型、另一量化及 NVIDIA 平台，不能据此给 A770 预测提升。其共享引擎还包含较新的 Strata 上游改动；下面区分新增引擎的设计与共享引擎的能力，不把所有差异归为 PolyStrata 原创。[项目说明][poly-readme]

| 顺序 | 借鉴点 | 主要影响 | 本地差距与最小动作 |
| --- | --- | --- | --- |
| 1 | 多个预填充块按层执行，复用暂存权重 | 多块 prompt 的 TTFT | 本地仍是块在外、层在内；先统计重复上传字节，再决定是否调整调度 |
| 2 | 缓存更新的选取、提交与生效分开 | decode | CUDA 已有可选异步更新，Intel 路径已有异步复制但没有对应后台提交状态机；先量化主线程成本 |
| 3 | 首轮响应后保存专家热度，后续限频保存 | 重启后首轮、不同任务切换后的缓存命中 | 已有保存及载入接口；先用现有配置，必要时只补首轮保存时机 |
| 小内存时 | 映射页回收、有限 RAM 专家预算 | RAM 占用、避免换页 | 适合小内存部署；当前 device-plan 路径要求完整镜像，不能只降低镜像上限 |
| 锁页不足时 | 按热度锁定非显存驻留专家 | 长 prompt、部分 PCIe 分流 | 本地 GGUF 镜像已按 profile 优先装入，完整镜像时不增加覆盖率 |

## 1. 预填充跨块复用：最有针对性的调度借鉴

`strata-poly` 的 [`Engine::read()`][poly-read] 把多个调用依次送过同一层，再进入下一层。前一调用上传的专家暂存在设备上，后一调用尽可能继续使用。设备保留两块残差；更多调用的残差暂存在 pinned RAM，以独立复制流和事件安排换入、换出。检查点也逐层保存，避免检查点强制结束整段读取。[设计与测量说明][poly-read-doc]

这里的关键是**减少同一层权重的重复上传**，而非单纯增加复制流。暂存区装不下一层时仍会有多轮搬运，源码另外判断暂存区上一轮内容是否能复用；不是每层永远只复制一次。

本地 [`Prefill::run()`](../sycl/src/prefill/prefill.cpp) 在第 1849 行按 chunk 循环，第 2320 行再按层循环。一段输入被实际切成多块时，同层流式权重可能重复搬运。`STRATA_PREFILL_FIRST` 还会主动产生一个较短首块，以覆盖 PLE 读取，因此不能仅看 `--prefill` 配置就判断有几块。单块输入没有跨块复用收益。

建议先复用现有预填充计时和复制统计，记录每块、每层的专家集合、实际上传字节、暂存容量和 PLE 准备时间。如果相邻块确实重复上传大量权重，再选两个块的纯文本输入做隔离原型。只交换循环顺序不够：必须保留 HC 残差、QSA / GDN / PLE 状态、MTP 状态与检查点的正确时刻，也要处理取消后的部分状态。

本地已经有[借用专家缓存作为预填充缓冲](../sycl/src/program/generate.cpp)和[FP16 双专家调度](OPENVINO_OPTIMIZATION_RESEARCH.md)。这两项不能再次算作新收益。更大的暂存区会挤占专家缓存，首块合并也可能损失 PLE 读取重叠，需把 TTFT 和随后的 decode 一起测。

**判断：值得先做流量统计；若成立再改调度，工作量中到大。** 不以外部模型的预填充倍率作为本地目标。

## 2. 缓存更新：先找主线程工作，再考虑后台化

PolyStrata 的共享引擎支持 `--adapt-async 1`，新版还覆盖全 RAM arena 的 copy-in-only 情况：先撤销被覆盖槽的驻留身份，复制完成后再公布新专家。选取、复制提交、完成确认各有明确边界。作者报告 RTX 3090 + Ryzen 5 5600X 的冷 prompt decode 提升 7%–11%，这是该平台和配置的结果。[实现条件与测量链接][poly-async]

本地 CUDA [`generate.cpp`](../src/program/generate.cpp) 已有 `adapt_async`、后台任务和提交阶段，不能称为全仓库缺失。Intel [`generate.cpp`](../sycl/src/program/generate.cpp) 也已经把复制放到 `adapt_stream`，通过事件和 `pending` 延后公布驻留；缺口是主线程仍负责选取和逐项提交，没有对应的 `--adapt-async` 状态机。**已有异步 DMA 不等于已经隐藏主机提交成本。**

本地 [`FileExpertSource::commit_exchanges()`](../sycl/src/core/expert_source.cpp) 仍会执行主机 `memcpy`。共享引擎的[所有权轮换][poly-rotation]支持按不同 blob 大小管理空闲缓冲，本地共享头只支持等大小的初版，而 Intel 实现没有接入。但要区分实际来源：当前常用 GGUF pinned mirror 路径并不使用这套 complement 交换，不能靠移植轮换消除一笔原本就没发生的复制。

建议先在完整请求中分别统计选取、提交、等待、主机复制的耗时和专家数量。若瓶颈是选取或提交，从单 GPU、完整不可变镜像的 copy-in-only 版本开始，不新增通用调度器。若是 complement 的主机复制占主导，再评估所有权轮换。

异步更新可能改变专家在哪个窗口进入显存，进而改变计算路径及舍入结果。采用前需要固定生效边界，保护尚在使用槽位的窗口，并检查取消、预填充借槽和会话恢复。不能通过直接删除 `.wait()` 获得候选。

**判断：可作为较小的 decode 候选，但必须先证明主线程成本存在。** 最新[原生后端记录](ORCA_NATIVE_BACKEND_STATUS.md)已排除其观测范围内的运行时锁获取，不能再把外部异步收益解释为本地必然受驱动锁限制。

## 3. 专家热度及时保存：小改动，改善重启后的表现

`strata-poly` 的 [`main.cpp`][poly-profile-loop] 把首次保存计时设为已经到期，完成请求后保存，随后按 10 秒限频；[`save_profile()`][poly-profile-write] 通过临时文件和 `std::filesystem::rename` 更新已有 profile。外部记录中，Gemma 4 在已有热度的启动中，所测回答从 68 增到 79 tok/s；这是 RTX 4070 Laptop 8 GB 上该回答的启动状态差异，不能当作持续热态加速。[记录][poly-profile-doc]

本地已有 `expert_profile_save`、`expert_profile_save_every` 以及载入 profile 的接口，[写入](../sycl/src/core/expert_cache.cpp)也已经使用 `std::filesystem::rename`。不需要再写一套热度格式或替换文件逻辑。差异主要是[保存时机](../sycl/src/program/generate.cpp)：默认 10 分钟、下一请求前检查，以及正常退出。短会话或强制结束可能没有机会留下新热度。

最小动作是先用现有配置缩短保存间隔，确认日志有保存、下一次启动确实读入保存路径。现有定时检查发生在下一请求前，所以缩短间隔仍不能保证只有一个请求的会话已落盘；若这是实际使用方式，再补“首轮完成后保存，之后限频”这一处逻辑。

测量应比较相同初始 profile、相同缓存容量的独立启动，保留首轮和热态结果。此项不改善同一进程内已经预热的重复请求，profile 也可能不适合另一类任务。

**判断：成本最低，优先用于改善日常重启体验；不作为持续 decode 内核优化。**

## 4. RAM 预算与按需锁页：保留为小内存方向

新增引擎会回收已经上传的 dense 权重映射页，并在请求间选择性回收显存专家的映射页；还缩小 pinned staging、归还长 prompt 的临时 host 缓冲。可选 `--ram-experts-mib` 对未驻留显存的专家设置 RAM 预算，用热专家映射和按大小分类的读取槽补足。源码在 [`trim()`][poly-trim]、RAM pool 和 [`drop_pages()`][poly-drop]。[说明和测量][poly-memory]

作者在 RTX 4070 Laptop 8 GB、32 GB RAM、Windows 11、Qwen3.6 UD-Q3_K_M 上报告：32K prompt 后的进程工作集由 17.9 降到 13.1 GiB；额外限制专家 RAM 到 6144 MiB 时，另一次测试中请求间工作集由 12.8 降到 7.1 GiB，但回答慢约 3%–14%。工作集下降不等于物理内存净回收同样大小，映射页还可能留在系统文件缓存。

对当前 A770 路径有三个限制：

- 本地已有 `STRATA_MIRROR_MIB` 和 [`GgufExpertSource::mirror()`](../sycl/src/core/gguf_expert_source.cpp)，不是缺少上限；缺少的是有限预算下仍高效、兼容设备计划的完整读入策略。
- `STRATA_VERIFY_ADAPT` + `STRATA_VERIFY_NO_HOST` [明确要求所有专家都有镜像](../sycl/src/program/generate.cpp)，包括将来会从显存淘汰的专家。直接减小镜像上限会失败，不能作为当前配置的一项开关优化。
- 当前测机有 256 GiB RAM；为此新增读取线程、RAM pool 和更多槽位管理不划算。现有预填充已经借用专家缓存，外部固定 staging 缩小所节省的显存也不能照搬。

共享引擎的 [`STRATA_PIN_BY_NEED`][poly-pin] 则把 Windows 有限的锁页预算留给更热、未驻留显存的专家。本地 Intel 镜像已经按 profile 优先放未驻留专家，并在设备自适应模式补齐所有专家；完整镜像时没有新的锁页覆盖率收益。只有锁页受限、部分镜像的配置值得继续比较。

**判断：小内存部署有价值，当前性能主线暂缓。** 也不要把匿名 pinned allocation 当作可丢弃的只读文件映射，直接套用 `MADV_DONTNEED` / 工作集回收。

## 不必重复做的部分与验证顺序

本地已有图重放、grouped 专家核、路由预读、缓存热度、借槽预填充和会话缓存；`serve/winjob.py` 也已处理 Windows 电源节流。PolyStrata 的实现可用于核对边界，重新实现这些功能本身没有收益依据。

外部的扩大推测窗口、稀疏 GDN 检查点、专家尾部裁剪属于另外的折中。本地已有 MTP 策略和相关实验，裁剪还改变模型输出；这次没有证据支持直接扩大窗口或放宽裁剪。页式上传环的事件所有权设计值得参考，但外部 AMD stale-data 问题不能视为已经在本地复现。

建议先做两项只读统计：多块预填充的重复权重上传，以及 decode 缓存更新的主线程耗时。若要从最小实现开始，先补 profile 首轮保存；若要攻 TTFT，再依统计结果决定跨块调度。

后续测速复用现有工具：Short、Code2K、Prose2K 和多块长输入，固定专家槽数、KV、MTP、profile 和请求顺序；记录实际块数、TTFT、decode、完整请求、显存最低余量。先通过完整输出与状态恢复检查，再作相邻基线和独立复测。当前[性能记录](A770_PERFORMANCE.md)的单场景至少 1%、噪声范围和余量规则继续沿用；跨块调度和后台提交尚待这些验证。

## 本地落地：共享主机代码的两个小改动

修改 [`sycl/src/program/generate.cpp`](../sycl/src/program/generate.cpp)，通过现有 `prepare.py --engine` 同时进入原生 DG2 与 Orca L0。缓存选择仍按原来的热度排序、大小兼容条件和收益门槛运行，只为每种专家 blob 大小保留淘汰列表的扫描位置。已经消耗或容量不足的条目在本轮不会再次可用，可以永久跳过；每轮清零游标。选择扫描由最坏 `候选数 × 槽数` 降为 `大小种类数 × 槽数 + 候选数`，排序成本不变。分类只在启动时建立，最多每层一个游标；没有新增线程、依赖或配置项。

启用 `expert_profile_save` 后，首个正常完成且产生输出的回答结束时保存一次，之后沿用原来的定时和退出保存。写失败会在后续正常回答后重试；取消不触发首次保存；间隔设为 `0` 仍只在退出时保存。文件格式、临时文件替换和下一次启动的载入接口沿用现有实现。直接启动引擎时使用 `--expert-profile-save <路径>`，经 Python 服务启动时使用现有 JSON 配置键。

运行 `python tools/test_adapt_selection.py`，从实际引擎源码抽取选择代码，与从头扫描的原实现逐项比较；4,006 组数据全部相同，覆盖不同 blob/槽位大小、热度相同、收益门槛、槽位耗尽和换入数量上限。还抽取实际保存逻辑检查首次、定时、重试、取消、零间隔、尚在复制的专家和关闭保存等情况。加 `--bench` 可看扫描次数和插桩自检耗时；这些耗时不作为端到端速度结论。48 × 512 的两个容量不足构造中，扫描次数分别从 50,158,162 / 51,067,570 降到 22,799 / 22,765；有 32 个可用换入的构造从约 528–533 降到 84–93。这些是构造数据，不能当作模型运行时的实际扫描次数。

Windows、Intel Xeon E5-2696 v4、256 GiB RAM、A770 16 GB 上，原生和 L0 分别重新编译基线、候选的主程序，复用各自相同的引擎库和同一套 1,242 个数学 zebin。基线仅回退这次的功能改动，保留工作树已有修改。固定 5,771 槽、FP16 KV、MTP 4、step/last 门槛 0.5、累计门槛 0、每轮最多交换 32 个专家。每个后端独立做基线/候选/基线，Short 每组预热 10 次、保留 5 次；各组再运行 Code2K、Prose2K，各生成 64 个 token。90 次 Short 都与 76 token、57/57 草稿的固定锚点相同；12 次 2K 请求的完整 token 序列、停止原因、草稿数在各自后端的三组间相同。

| 后端 | Short 基线 tok/s | 候选 tok/s | 变化 | 前后基线漂移 |
| --- | ---: | ---: | ---: | ---: |
| 原生 DG2 | 47.72 | 47.55 | -0.37% | -0.04% |
| Orca L0 | 47.93 | 48.29 | +0.74% | +1.99% |

基线列是前后两组保留样本中位数的几何平均；decode 不含初始化和 prefill。两条路径 Short 的 TTFT 分别约为 889.8 → 889.4 ms、897.6 → 887.6 ms，L0 的 TTFT 基线本身漂移 -3.31%。时钟未锁定，每个后端仅一轮对照，**没有证据宣称整机吞吐稳定提升**；这次落地的性能依据是消除选择扫描的最坏退化。测速关闭了画像保存，画像行为另用独立进程验证。

两条后端各自通过六类画像检查：旧基线在退出时保存；候选在 QUIT 前完成首次保存且下一轮不重复写；零间隔仅退出保存；输出目录缺失时写失败、补建后重试成功；取消不触发首次保存、后续正常回答会保存；重新启动载入新画像后仍产生精确的 Short 输出。文件均包含 24,576 个合法且不重复的专家条目。初次统一脚本达到 600 秒超时，保留完成的模型对照，重跑中断的原生重试用例，再串行完成余下检查；该超时和续跑原因也记入原始记录。

原始构建、协议与日志在 `build-orca-polystrata-20261103-v2/`；[精简测量记录](../bench/results/a770/polystrata-host-2026-11-03.json)保存源码、可执行文件和库的摘要、各次结果及画像检查。现有生产配置、可执行文件和专家画像均保留。跨块预填充、后台选取/提交、有限 RAM 池不在此次实现内。

## FP16 双专家激活融合：推广到原生路径

后续优化 [`sycl/orca/gemm.cpp`](../sycl/orca/gemm.cpp) 的双专家预填充：一次核启动完成两个专家的 SwiGLU 激活，同时准备 Down GEMM 的尾部补零，复用现有 GEMM workspace，不增加 scratch。对齐的 pair 由 4 次启动减为 3 次，需要尾部补零的 pair 由 6 次减为 4 次；这只是 pair 内的计数，不是整个 prefill 的降幅。矩阵乘法的 K 顺序、FP16 饱和及舍入保留；原有 8 个矩阵 zebin 与基线逐字节一致。

本轮按用户要求使用实际 **6,561 个专家槽**，命令请求 `--expert-cache 6250`，模型取整后缓存为 9,001 MiB。参数单位是专家数。FP16 KV、8,192 上下文和预填充上限、6-token 验证窗口、MTP 最多 4、lookup 3、每轮适配最多 32、PCIe 比例 0.16、无 prompt cache，各组相同。沿用历史基准的 MTP 累积门槛 0，和生产的 0.5 不同。此前 5,771 槽的记录保留为历史数据，不混入本轮比较。

第一次 6,561 槽筛选中，原生 Code/Prose 分别回退 6.03% / 2.92%，L0 提升 2.12% / 2.48%。但该原生候选组的 Short 并不走这次融合，prefill 也从前后基线的 925.4 / 939.9 ms 增到 1,367.0 ms。因此这轮数据不能单独证明融合核拖慢原生。旧样本全部保留，没有事后剔除首轮慢请求。

重新独立启动原生 A0/B/A1：每组先运行 Short，再分别运行一次 Code2K、Prose2K 预热并保存，然后各保留两次请求。Code prefill 的前后基线几何均值为 31,097.94 ms，候选为 30,766.55 ms，吞吐提升 **1.08%**；Prose 为 30,208.12 → 29,738.30 ms，提升 **1.58%**。前后基线漂移仅 +0.13% / −0.12%，TTFT 的改善接近相同。再独立做原生 B0/A/B1，每组预热后各保留一次：Code 为 31,231.20 → 30,756.17 ms，提升 **1.54%**；Prose 为 30,439.80 → 29,538.94 ms，提升 **3.05%**。候选前后漂移 +2.15% / +1.40%，TTFT 改善 1.54% / 3.05%。两轮全部保留请求的完整输出、停止原因和草稿接受数一致。源码据此对原生和 L0 同时启用融合，取消先前只对原生保留旧流程的分支。显式预热后的结果与初筛方向不同，但尚不能将初筛回退的原因只归于预热。

L0 另做独立 B0/A/B1 反向复核，Code/Prose 各组各一次、全部保留：prefill 提升 **2.40% / 3.50%**，候选前后漂移 +0.24% / +0.76%。原生默认每 64 个混合操作提交一批，并通过 owner 线程编码、上传本地参数；L0 使用自己的提交路径。减少启动会改变两者的提交成本和批边界，这些是已核对的源码差异，还不是对收益差异的因果证明。

既有 [`sycl/orca/check.cpp`](../sycl/orca/check.cpp) 扩展至 12 对形状，两后端分别通过 **504 项完整输出检查**，包含 GU/H/Y 字节一致、不同权重、尾部与 guard、正负 FP16 饱和、异步、图录制及回放、非法输入拒绝。`--bench-pair` 额外记录 6 对形状的即时提交及回放中位耗时。主机提交和 GPU 执行重叠，不能把完成耗时减去提交耗时当作独占 GPU 时间。

两后端分别完成算子 A0/仅融合激活/激活加尾部补零/A1 对照，每次保留 7 批、每批 32 对相同缓冲区。32/32 行时，原生即时完成耗时 528.64 → 546.41 μs，回退 3.25%，基线漂移 +0.35%；图回放 473.92 → 474.04 μs，几乎不变，漂移 −2.63%。L0 同形状即时耗时 735.86 → 702.54 μs，提升 4.74%，漂移 −0.64%；图回放 452.79 → 452.19 μs，提升仅 0.13%，漂移 +0.49%。启动数相同的减少并不保证两条路径相同的收益；这个固定权重和参数的微基准也不能直接推算模型吞吐。后续原生应优先隔离参数处理、提交批次和 CPU 等待成本。

另做精简索引的原生候选，通过 504 项数值检查，但单次无夹基线的算子诊断未显示一致正向信号，因此未推广到源码，也未宣称整模型收益。[精简测量记录](../bench/results/a770/prefill-pair-activation-2026-11-03.json) 保存初筛、原生预热对照与反向复测、L0 反向复测、算子对照和构建摘要；原始日志位于 `build-orca-pair-activation-20261103/`。生产 EXE、配置和专家画像均未替换。

6,561 槽属于固定实验容量，未修改生产自动容量或 reserve。初筛 1 Hz 物理空闲显存最低样本为 735.8 MiB，原生反向复测最低为 711.8 MiB，均低于此前 1,024 MiB 的余量标准；READY 可用显存是另一种计数器。时钟未锁定、样本数量有限，不将两个 2K 场景推广为 decode 或长上下文的稳定收益。

## 原生双专家编码的线程交接

在上述融合版基础上，进一步修改 [`fp16_pair::execute()`](../sycl/orca/gemm.cpp)：先在原调用线程处理既有的延迟操作，再通过现有 `OwnerExecutor` 一次编码一个 pair。对齐时 3 次、需要尾部补零时 4 次核编码交接合为 1 次；这不包含此前事件的发布和结束等待，也不是 GPU 提交次数。GPU 等待仍由原调用线程执行，原生的 64 操作批次上限保留。只增加 9 行主机代码，复用相同的 GPU 核文件，不改矩阵运算、激活、精度或 scratch。

两条后端重新编译检查程序，分别通过 504 项完整输出检查。新增前置 host callback 检查：`execute(finish=true)` 返回前，callback 必须已经完成。原有异步、图捕获及回放、guard 和非法输入检查保留。原生算子 A0/B/A1 中，32/32 行即时完成耗时 542.96 → 529.45 μs，吞吐提升 2.55%，基线漂移 +0.48%；8/16 行回退 1.62%，漂移 +2.33%，因此仍以整模型确定采用范围。

使用相同机器、实际 6,561 槽和上一节参数，基线是已融合激活及尾部补零的版本。原生先做 A0/B/A1，再独立做 B0/A/B1；每组先运行 Short 和两种 2K 输入各一次预热，再各保留两次请求。预热数据单独保存，不事后删除慢样本。结果是相对上一轮融合版的增量：

| 原生 prefill 场景 | A0/B/A1 吞吐变化 | 独立 B0/A/B1 吞吐变化 |
| --- | ---: | ---: |
| Code2K | +1.06% | +1.39% |
| Prose2K | −0.48% | +0.39% |

Code 的 TTFT 改善 1.05% / 1.39%。首轮前后基线漂移为 Code −0.57%、Prose −0.43%；反向复测前后候选漂移为 +0.28% / +0.58%。24 次保留请求的完整输出、停止原因、草稿接受数一致，Code 每次 9,159 个 pair、Prose 每次 8,565 个。Code 的两轮增量超过 1%，Prose 均在 ±1% 内且方向不一致，故采用原生主机改动，但不宣称 Prose 有稳定收益。L0 的实现保留。

## 原生参数生成：复用最近的 local-ID 布局

修改 [`arguments.hpp`](../orca-l0/src/drm/arguments.hpp) 和 [`recording.inl`](../orca-l0/src/drm/recording.inl)：同一个核的 local shape 不变时，复制已有 `last_indirect`，只更新非 inline 的 cross-thread 参数。shape 变化或缓存为空时，沿用完整生成函数。每个核只额外记录三个 local 维度，复用已有 CPU 参数缓存，不增加 GPU 缓冲区。入口参数校验、不可变捕获、弱引用失效检查和本地参数镜像上传仍由原来的路径处理；inline 参数仍交给 dispatch 编码。本次针对原生 DG2，vendor L0 路径不涉及这段代码。

在同一台 Xeon E5-2696 v4 上，独立 CPU A0/B/A1 微测使用 packed SIMD1、固定 local shape、每次变化的 cross-thread 参数，每组预热一批、保留七批，每批 32,768 次。256-thread 参数包生成的基线几何均值为 **2.797 μs**，候选 **0.322 μs**，耗时降低 **88.48%**，前后基线漂移 −2.90%。16/64-thread 对应为 0.288 → 0.103 μs、0.789 → 0.119 μs；64-thread 的基线漂移达 +11.92%，不能据此给出精确稳定的降幅。这些只测 CPU 参数包生成，不包含完整参数打包、驱动提交或 GPU 执行，也不能换算成模型提速。

既有 CPU 自检增加 120 个完整字节比较，直接调用实际缓存函数与原始生成函数对照，覆盖 packed SIMD1、SIMD8/16/32、硬件 local ID、无 local ID、inline 长度、重复和变化的 1D/3D shape、inactive lane 与 padding，并拒绝错误参数长度和零 local。当前工作树源码在 Windows 和 Linux 均编译通过；Linux 三项 CPU 检查通过。隔离 runtime 通过 15 项检查，另通过 17,000 次不可变参数捕获、64 次动态录制提交及 504 项原生完整输出检查。当前工作树完整 runtime 重新链接后，也通过 504 项原生 GPU 输出检查。

整模型基线是上一节的双专家编码合并版，候选只给同一已知 runtime 移植本次差异，复用相同的引擎对象、owner 合并对象和 GPU 数学核。继续使用实际 **6,561 槽 / 9,001 MiB**（请求 `--expert-cache 6250`）和上一节的固定参数。A0/B/A1 与独立 B0/A/B1 每组各预热两种输入一次，再各保留两次；全部 24 次保留请求与 12 次预热的完整输出、停止原因、草稿接受数一致。

| 原生 prefill 场景 | A0/B/A1 吞吐变化 | 独立 B0/A/B1 吞吐变化 |
| --- | ---: | ---: |
| Code2K | +0.51% | +2.11% |
| Prose2K | +0.77% | +0.67% |

TTFT 分别改善 0.50% / 2.10%、0.77% / 0.67%。首轮 Code/Prose 的前后基线漂移为 −0.97% / −1.24%，反向候选漂移为 +0.27% / +1.12%。本轮以两轮 prefill 和 TTFT 方向均为正、完整输出一致、数值检查通过作为源码采纳依据，**已采纳该改动**。1% 仅作为收益确认标准，不作为采纳的硬门槛；两种输入均未达到“两轮都至少改善 1%”的标准，因此不宣布稳定的端到端提速。图回放直接使用已录制参数，不会重新生成 local ID；没有 decode 或长上下文收益结论。

## 原生提交：完整参数只打包一次

原生 `Runtime::append()` 原先完整打包两遍参数：第一遍在资源分配前校验输入，第二遍在资源就绪后填入隐藏地址。保留第一遍及其校验，第二遍改为 [`bind_base_arguments()`](../orca-l0/src/drm/arguments.hpp)，只补齐全局、常量和 private 三类隐藏基址。每次 append 的完整参数打包由 **2 次降为 1 次**，避免重复生成 cross-thread 缓冲区、读取调用者参数和扫描驻留分配。改动只涉及原生 DG2 参数处理，不增加缓存、配置项或 GPU 缓冲区。

CPU 自检新增 32 个完整字节比较，对照保留的原始完整打包函数，覆盖普通 GPU 指针、CPU 捕获指针、动态 SLM、无隐藏基址、1D/3D local shape、零地址、普通和 canonical 地址、非零后重新清零，并拒绝错误的 cross-thread 长度。隔离 runtime 的 15 项检查、17,000 次不可变捕获、64 次动态录制提交通过；额外通过 private 内存、原子操作、device-local 复制、48 次动态 SLM GEMV 和 144 次 XMX GEMM 的完整输出及 guard 检查。隔离候选和当前工作树完整 runtime 分别通过 504 项原生 GPU 输出检查；当前工作树的 Windows CPU 自检、Linux 三项 CPU 检查均通过。

在 Windows、Xeon E5-2696 v4、256 GiB RAM、A770 16 GB 上，以上一节已采纳的 local-ID 缓存版为基线，保持同一组引擎/owner 对象和 GPU 数学核，候选只移植本次参数处理差异。实际仍为 **6,561 槽 / 9,001 MiB**，请求 `--expert-cache 6250`，其余参数沿用上一节。原生 A0/B/A1 每组先运行 Short，再分别预热 Code2K、Prose2K 一次，随后各保留两次、每次生成 64 token。12 次保留请求与 6 次预热的完整输出、停止原因和草稿接受数一致；每次 Code/Prose 的 pair 数仍为 9,159 / 8,565。

## 原生资源登记：复用经过验证的位置提示

原生运行时为一次录制登记所用资源，原先每次都在线性列表中查找去重。在 [`arguments.hpp`](../orca-l0/src/drm/arguments.hpp) 的每个 `RecordingStorage` 中增加一个位置提示：只有索引未越界、且当前列表该位置的指针确实等于目标资源时，才直接返回；否则仍按原来的线性查找登记，并更新提示。重复命中为 O(1)，新资源或交错列表仍可能为 O(n)。列表清空、移动及不同列表交错使用不会凭旧提示跳过登记，资源顺序和原有 fence 跟踪保留。另在 [`recording.inl`](../orca-l0/src/drm/recording.inl) 的 GPU 地址范围查找命中后直接登记已找到的资源，省掉一次重复的 handle 查找。只增加一个 `size_t` 字段，复用现有容器。

CPU 自检增加 8,192 步对照，逐步增长到 257 个资源，在三个列表间交错登记、重复登记、清空及移动，每步与原始线性实现精确比较成员及插入顺序。隔离 runtime 的 15 项检查、17,000 次不可变参数捕获、64 次动态录制提交通过，另通过 private 内存、原子操作、device pipeline 和多队列内存检查。隔离候选和当前工作树完整 runtime 分别通过 504 项原生 GPU 输出检查；当前工作树的 Windows CPU 自检及 Linux 三项 CPU 检查通过。可运行的新增检查位于 [`drm_compute_check.cpp`](../orca-l0/tests/drm_compute_check.cpp) 的 `self_check()`。

上一节按字段的驻留提示仍需先扫描 CPU 映射，才检查捕获指针的 GPU 驻留范围。本轮在每个 Runtime 中增加两个 `uint64_t`，共 16 字节，记录成功加入的 CPU 映射的最小起点和最大末字节。地址落在边界外时，直接继续原来的 GPU 驻留校验；边界内包括映射间的空隙，仍执行完整、有序的 CPU 映射扫描，再校验 GPU 地址，保留 CPU 转换优先的语义。上界采用饱和加法，避免溢出。

Windows 和 Linux 的成功主机分配、导入入口都会扩大边界；释放时不收缩。旧边界和空隙只会造成额外扫描，不会跳过有效映射；这部分仍有 O(n) 的上限。已有 GPU 范围验证及按字段的驻留提示继续使用，无新增依赖、配置或 GPU 缓冲区。改动限于 [`arguments.hpp`](../orca-l0/src/drm/arguments.hpp)、[`recording.inl`](../orca-l0/src/drm/recording.inl)、两平台 runtime 和原有 CPU 自检。

CPU 自检新增 4,096 步、24,576 次带边界/原始转换及非法地址拒绝结果对照，覆盖分配增删、清空后保留边界、重排、空指针、起点/末字节/越界、CPU/GPU 数值重叠及 `UINT64_MAX` 上界饱和。另增加 32 次聚合参数完整字节比较及两次捕获 CPU/GPU 指针参数包比较。已有 81,920 次驻留判断检查继续通过；隔离 runtime 的 15 项检查、17,000 次不可变捕获、64 次动态录制提交、private、原子操作、device pipeline 和多队列内存检查通过。隔离候选与当前工作树完整 runtime 各通过 504 项原生 GPU 输出检查，当前工作树 Windows CPU 自检及 Linux 三项 CPU 检查通过。

### C++20 协程对照

### 采纳标准库租约内存池

[`AllocationPool`](../orca-l0/src/drm/arguments.hpp) 已复用 GPU 缓冲，但原来每次领取仍分别分配主机 `Allocation` 对象及 `shared_ptr` 控制块。改为 `allocate_shared<Lease>()`，用每个池自己的 `std::pmr::unsynchronized_pool_resource` 复用固定尺寸的租约/控制块；返回指向租约内 `Allocation` 的别名 `shared_ptr`。最后一个强引用释放时归还 GPU 缓冲，旧弱引用保持过期状态。控制块在最后一个弱引用释放后才交回 PMR，池在 State 中仍先于强、弱租约声明，因而最后销毁。

沿用单一 host owner，未增加锁、GPU 缓冲、配置开关或依赖。PMR 会保留主机租约内存的峰值到 Runtime 退出；如将来需要缩减，应在所有录制、捕获及弱引用都清除后的明确边界释放，不能在仍有弱控制块时调用 `release()`。GPU 分配失败时，租约尚未绑定池，不会错误归还空分配；原来的先 reserve 再归还及 best-fit GPU 缓冲复用继续保留。

### Orca L0 改为 Rust：工程优势明确，速度收益待验证

**当前不建议为提速整体重写。** Orca L0 是 C++17 宿主调用 Level Zero C API；原生 DG2 则直接使用 Windows D3DKMT 或 Linux i915 DRM。数学核是已有的 GPU 程序。保持相同 GPU ISA、搬运字节、队列依赖和提交次数时，更换宿主语言不会自动改变这些成本；本轮没有 Rust 对照实现，无法给出提速百分比。

| 方面 | Rust 可带来的价值 | 当前边界 |
| --- | --- | --- |
| 所有权与生命周期 | 约束 Runtime、命令、分配的借用关系，在安全封装中阻止部分悬空引用和错误跨线程共享 | GPU 执行完成和 Host 可见性不是普通借用关系；仍需显式 fence、队列序号、租约及复用规则，`Drop` 不代表 GPU 已停止使用 |
| 内存与布局 | 值类型、切片、arena、按 owner 约束的引用计数可构成较小的安全 API | C++ 当前也能借用、预分配和池化；直接改成 `Arc<Mutex<...>>` 或每核跨 FFI 可能增加成本，性能收益应归因于具体布局与流程 |
| 并发与 async | 类型系统有助于明确哪些状态只能由 owner 修改，适合表达异步任务依赖 | Rust async 与 C++ 协程都不会自动增加 GPU 并发。当前已存在 staging 线程和异步 GPU 队列；同步交接也保证临时闭包存活，改成异步必须补上所有权 |
| 驱动与编译集成 | 可以把不安全代码集中在较小的底层模块 | Level Zero FFI、D3DKMT/ioctl、映射内存、命令字节编码仍需 `unsafe`；现有 C++/SYCL 编译期入口和数值核仍要保留，整体迁移增加构建、ABI 和双后端验证成本 |

若目的是安全性，可先试纯 CPU 的 zebin/元数据解析边界；它主要发生在加载阶段，不能拿其微测宣称 decode 更快。若目的是性能，应先在现有 C++ 中落实上面的参数准备和成组提交，再选择一个经过剖析证实占时的宿主组件做同接口 Rust 原型。跨语言边界采用粗粒度 C ABI 和不透明句柄，异常或 panic 不跨 ABI；保持相同 GPU 二进制、参数字节、队列顺序、槽数及阈值，验证完整输出和请求耗时。任何一版只改善启动、录制或局部 CPU 微测，都分别报告，不外推整个推理。

### 上传 staging 合并：局部收益未转化为模型收益

隔离修改原生 `Stream::flush_copies_locked()`：每次 flush 先计算 Host 快照的总容量，按 64 字节对齐领取一块 staging，再填满后发射各偏移的 GPU copy。生产者的内容快照保留，未减少 CPU 复制次数；操作数上限导致分段提交时，每个 segment 都保留同一租约直至完成。一个 flush 上限仍为 64 个、各不超过 128 KiB 的快照；注册 D2D 的相对顺序保持不变。未增加依赖或配置开关。

为避免混用不同内联适配器定义，先用只链接当前 runtime 的单翻译单元检查，再为基线和候选各完整重编译 **81 个 Host 对象**，两组均通过 **504 项 GPU 数值检查**，使用相同 PMR runtime 和 GPU 数学核。初次构建因原始头文件先于生成头文件而失败，修正搜索顺序后的 v1 成功；该次失败命令、日志及源码保留，没有覆盖失败记录或修改生产文件。另一次冻结文件重写遇到 Windows 文件共享错误，改为内容相等时不重写；这次只有工具执行记录，没有单独的失败构建结果文件。

已有 [`orca_queue_check.cpp`](../sycl/orca_queue_check.cpp) 增加混合检查：每轮 70 次 Host 上传，尺寸为 1/16/17/65/4,097/131,072 字节，穿插十次 D2D 消费，重复三轮；覆盖调用返回后改写 Host 输入、快照槽复用、非整齐偏移、提交切分及完整保护区。基线与候选分别在操作上限 **1/3/64/4,096** 下通过，共八次。该检查保留在源码中，候选适配器始终没有接入工作树。
